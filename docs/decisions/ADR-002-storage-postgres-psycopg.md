# ADR-002: Storage: Postgres with psycopg 3 and plain SQL migrations

- Date: 2026-11-02
- Status: accepted

## Context
Runs are trees of spans with JSON payloads, and reports need aggregates over them (pass rate,
token sums, p95). Postgres handles both with JSONB, and CI can run it as a service container.
psycopg 3.3.6 with psycopg-pool 3.3.3 provides `ConnectionPool`, `dict_row` and `Jsonb`.

## Decision
- Six tables: `schema_migrations`, `suite_runs`, `runs`, `spans`, `scores`, `model_cache`.
  Payloads (neutral requests and responses, tool arguments and results) are JSONB in
  `spans.payload`; semconv attributes are JSONB in `spans.attributes`.
- Ids: `uuid` for suite runs and runs (generated in Python with `uuid4`), `text` for OTel trace
  and span ids.
- Migrations: numbered files `src/agent_replay/db/migrations/NNN_name.sql`, each applied in its
  own transaction and recorded in `schema_migrations`, by a small runner in `db/migrate.py`.
- All SQL lives in `db/runs_repo.py` and `db/cache_repo.py`, with bound parameters only.
- A sync `ConnectionPool` for the CLI and the FastAPI routes; no async pool.

## Alternatives considered
- SQLAlchemy and Alembic: heavier than the handful of queries the CLI and API need.
- SQLite: simpler, but weaker JSON aggregation, and CI already has a Postgres service.
- An async pool: no concurrency need in a CLI and a read-only API.

## Consequences
- Schema changes need a new numbered SQL file; nothing is autogenerated.
- Tests need a real Postgres (the compose `db` service locally, a service container in CI).
